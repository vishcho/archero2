# 視覺抽取規則

## 通用契約

- 每筆保留來源檔名；模糊值記 `uncertain` 或 note，不挑合理值猜測。
- 忽略操作按鈕、分頁、讚數、貨幣、倒數等非目標 UI。
- 不因版面對稱、索引或歷史規律推導看不到的關係。

## 資格排行榜

抽取 rank、name、可見 title、time。底部固定本人列不是捲動內容。用相鄰畫面重疊 rank 合併，確認目標排名唯一且連續。頭像遮字時找相鄰畫面或清楚名片；仍不清楚就留未知。

## Top 64 名片

優先讀 `player_id` 並保存為字串。ID 不清不得入庫；完整性看唯一 ID 數而非圖片數。相同名稱不同 ID 是同名多人；相同 ID 名稱不同才進入改名／OCR variant 裁決。累積欄位跨時間下降要回看。

名片彈窗背後常可看見該列的排行榜名次與時間（彈窗上下緣露出）。可讀時記為
`rank_hint` / `time_hint`，用於與 `qualifier[]` 交叉驗證——這是不依賴同一次
名片判讀的獨立訊號，特別適合裁決同名多人。讀不到就略過，**不得由檔名順序推定**。

## 賽前對陣

賽季資料的 `groups[].players` 依畫面由上而下、先左後右保存。這是籤位顯示順序，不是 R1 配對規則。禁止從索引推 A/B/C/D、排序玩家，或在賽季資料中預填 `matches: []`。

下注預覽使用獨立的 `tmp/<season>-matchup.json`。只有畫面能逐場追蹤玩家之間的連線時，才直接記為 `groups[].matches[]`；每場保存 `slot`、`p1`、`p2`，並優先帶入 `player_id`。若連線不可辨識，停止產生下注 matchup，不得用固定版面規則或相鄰索引補出 A/B/C/D。

## 淘汰賽與總決賽

結果樹與七場彈窗互驗。彈窗戰力是賽時快照；結果樹 current power 可能隨拍攝日增長，不可混用。

但**同一批截圖內**的樹狀圖與 `data/` 之間沒有增長空間——兩者同次拍攝。樹狀圖與
`data/` 的 `champion_current_power` 不一致時一律回看原圖，不得歸因為增長。
樹狀圖上同一位冠軍通常在多個節點重複顯示同一數值（round4 為 4 處），可自我驗證。

### 回合歸位只能靠樹狀圖版面（round5 實測）

**對戰彈窗中央的字串是階段標籤，不是回合名。** 它在同一批內是常數、批之間卻不同：
round5 淘汰賽批 56 張全部寫「決賽」（包含 R1），總決賽批 8 張全部寫「展示期」。
看到它就跳過，不得據以判斷場次；把它當回合名會得出「第一張是決賽」這種自洽但完全
錯誤的結論。

樹狀圖是回合的唯一來源，讀法：

- 最左欄 4 個 + 最右欄 4 個節點＝ R1 的 8 位參賽者，無放大鏡圖示。
- 往內一層（左 x≈275／右 x≈635）＝ R1 勝者；再往內（x≈450 上下各一，節點上方有
  **白色小皇冠**）＝ R2 勝者；正中央帶**金色皇冠＋桂冠光暈**者＝組冠軍。
- **放大鏡圖示恰好 7 個，各掛在該場勝者的節點上**——這就是 7 場的定位錨。
- slot 對應版面：左上=A、左下=B、右上=C、右下=D；R2 upper = A 勝者 vs C 勝者，
  R2 lower = B vs D。
- 節點頭像是玩家自訂圖片（獎盃、卡通角色都有），**不是**名次或排名標記。

**彈窗與場次的對位靠選手配對，不靠拍攝順序。** 先從樹狀圖建出 7 場的雙方名單，
再用名稱配對把 7 張彈窗各自歸位；順序無關，缺漏與多餘都會自己浮出來。

### 已發布的下注快照是免費的 slot 權威錨點

`data/predictions/star-cup/<season>.json` 的 `groups[].picks` 已含逐場 `slot` 與雙方
`player_id`，是賽前獨立產出的資料。把樹狀圖讀出的四組 R1 配對（多重集）去比對它，
就能把 A/B/C/D 釘死，不必依賴任何索引推導——**且它順便驗證了樹狀圖的判讀**。
只有找不到快照時才退回純版面判定。

round5 的 `groups[].players` 恰好是**連續配對**（A=[0][1]、B=[2][3]、C=[4][5]、
D=[6][7]），與 round4 的**交錯索引**（A=[0][2]、B=[4][6]、C=[1][3]、D=[5][7]）完全
不同。兩屆相反，是「不得由 players 索引推導配對」最直接的證據。

### 戰力不是單向遞增

「賽時戰力不得高於樹狀圖目前戰力」**不成立**。round5 G7 `고른주부J` 為 8/14 19.18M
→ 賽時 19.66M → 8/20 樹狀圖 19.19M，三個值都經回看確認：玩家為該場換裝後又換回。
把這種下降當成誤讀會誤判。反之，**同一位選手在同組跨場的賽時戰力必須相同**
（同組 7 場同時結算，快照同一時點），不同就是有一邊讀錯。

同場雙方戰力剛好相同是可能的（round5 G1 R1-D 兩人皆 16.14M，回看確認），
但它與 round4 那個「整組複製單一值」的 bug 表徵相似，遇到就回看一次。

**總決賽的賽時戰力不必等於各組 `champion_power`。** round4 兩者 8/8 相等，但那是巧合
不是不變量：round5 為 6/8 相等，`ZᶻZ`（35.28→37.49M）與 `RV297`（22.99→23.07M）
在分組賽（8/20）到總決賽（8/22）之間成長。可用的不變量是排序——
**分組賽時 ≤ 總決賽賽時 ≤ 總決賽結果樹目前戰力**——加上「同一人在總決賽 7 場內的
賽時戰力必須相同」。用相等當硬性檢查會產生假陽性。

### 跨批改名要用三重訊號定身分

結果批（賽後）與對陣批（賽前）相隔數日，選手會改名。round5 有 7 筆，
其中 3 位是原本同名的 `龍×똥꼬` 各自改成不同名字。判定身分不要靠字形相似度：

1. **組內集合減法**——同組其他 5–7 人名稱完全對得上，剩下的必然對應剩下的 player。
2. **下注快照的 slot 錨點**——樹狀圖某個版面位置的配對對應快照哪個 slot，
   即可定出該位置那兩人的 `player_id`。
3. **戰力比對**——樹狀圖目前戰力 vs 對陣批戰力。round5 三位同名者為
   9.97M／17.77M／13.21M 與賽前**完全相等**，直接把長期的同名歧義解掉。

三個訊號互相獨立；只有一個成立時不要下結論。改名寫入慣例見
[`validation-and-import.md`](./validation-and-import.md)。

總決賽由外往內讀：最外 8 格為八強，往內 4 格為準決賽參賽者，皇冠兩側為決賽參賽者，中央為冠軍。亞軍是決賽敗者。名次多重集為 `1,2,3,3,5,5,5,5`；三四名戰不拆並列名次。

總決賽八人須等於八組 champion；冠軍、決賽勝者與頂層 champion 須一致。

## Unicode 與 OCR

保留 `ARKΛ`/`ARKA`、`FLΞX`/`FLEX`、`ᴬᴷ`、`ᶠˣ`、`丨`/`｜`/`|` 等原始差異。裁決優先序：清楚名片 → 同批相鄰原圖 → `players.json` names/ocr_variants → 保留不確定。改名進 `names[]`，OCR 誤讀進 `ocr_variants[]`。

### 委派用字形清單

委派子代理判讀時，把下列清單複製進 prompt，並要求「記錄實際看到的字形，
兩種讀法都合理時擇一並在 note 註明另一種」。本清單為歷次實際誤讀累積：

```text
力 / 办 / 刃        剩 / 刺        隻 / 皇        仔 / 仨
雉 / 雄 / 雏        薯 / 署        放 / 破        融 / 秦
凜 / 濃            姒 / 奴        丫 / 丁 / Y
丨(U+4E28) / ｜(U+FF5C) / |(pipe) / I / l
× / ╳ / x / ✕      ᴬᴷ / AK / I매I        ᶠˣ / ^fx        ᶻZ / ᴰᴳ
도 / 토   팡 / 광 / 땅   똥 / 돟 / 뚱   힘 / 힝 / 힐   ㅇ / o / 0
```

韓文小字與上標最易出錯；整段韓文被讀成中文（如 `똥꼬`→`琦笃`）是明確的模型能力不足訊號，該批應改用 Sonnet 重讀。
